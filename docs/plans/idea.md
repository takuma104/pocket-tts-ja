## 2. LSDを第一候補にする理由

### 既存のsamplerをそのまま活用できる

LSDを継続すれば、**Transformerだけでなく、連続latentの条件付き分布を生成するheadの重みも引き継げます**。日本語化では、テキスト表現とテキスト-音声の対応を大きく変える必要がありますが、その際にsamplerまで新しく学習し直す必要はありません。公式の言語FT経路も、そのような読み込みになっています。

一方、Driftingには時間条件がなく、LSDのheadとは入力構成が異なります。また、Driftingの学習は各位置で複数候補を生成し、kernelによる力を計算する方式です。**「JVPがないから、言語FTでも必ず速く・安定になる」とはまだ判断できません。** 日本語で比較するときには、steps/sだけでなく、同じ品質に到達するまでの計算量を見る必要があります。

### 現行コードには、DriftingのFTで注意すべき読み込み処理がある

前の回答で確認したコミット`41cbc84`では、`training/modules/builders.py`に、次の処理があります。

```python
if flow.num_time_conds != 2:
    # flow_netの重みを読み込み対象から除外
    ...
    dit_init(flow_lm.flow_net)
```

つまり、この`start_from_pretrained`経路では、**Driftingの重みから始めてもheadが再初期化されます**。さらに、`reset_text_embedding: true`との併用では、Embeddingのmissing keyを許容しないassertに引っかかる構造です。既存Drifting headを保持した日本語FTには、この分岐を修正する必要があります。

これはDrifting自体の問題ではなく、**現在の学習コードが「既存LSDから別目的へ切り替える」場合を中心に書かれていることによる実装上の注意点**です。

したがって初回はLSDで日本語の基準モデルを作り、Driftingを試す際には、同じMimi・同じTokenizer・同じデータを使って比較するのがよいと思います。

### sampler headは凍結するか

**初回は凍結せず、既存重みを保持してFT**を勧めます。日本語への適応能力を、最初からhead固定で制限しないためです。

その後の比較実験として、同じ条件で`freeze_head: true`を試す価値はあります。「小規模データで音響品質が崩れる」「既存のheadを固定した方が汎化する」という結果が出るかもしれません。このフラグは実装済みです。

ここで、**headを再初期化することと、学習可能にすることは別**です。おすすめは「再初期化しない・学習はする」です。

## 3. Mimiは凍結。ただし、最初に日本語の再構成を確認する

Mimiについては、FT前に小さな評価を行うのが重要です。

日本語の音声を、**Pocket TTSに同梱されたMimi**に通して、

$$
x_{\text{日本語音声}}
\longrightarrow E_{\mathrm{Mimi}}(x)
\longrightarrow D_{\mathrm{Mimi}}\!\left(E_{\mathrm{Mimi}}(x)\right)
$$

という再構成音声を作り、元音声と比較します。Pocket TTSが使うのは量子化されたIDではなく、32次元の連続latentです。別の一般的なMimiチェックポイントへ置き換えて評価するのではなく、実際にFTで使用するものを調べる必要があります。

私なら、まず100〜200発話程度で、長音・促音・撥音・無声化した母音、高低の異なる声、ささやきや感情音声などを含めて確認します。

| 再構成音声の状態 | 次の判断 |
|---|---|
| 発音・声質とも十分に保たれる | **Mimiを固定したままTTSのFTへ進む** |
| 発音は正しいが、声質や高域の質感が悪い | TTSとは別にdecoder側の適応を検討 |
| 長短母音や促音など、音韻情報が明確に失われる | encoder／latent表現も含めた見直しを検討 |

この評価は、生成TTSの絶対的な性能上限を測るものではありませんが、**「日本語がうまく出ない原因をMimiに求めるべきか」の切り分け**には有効です。

### encoderを最初から動かさない理由

既存のFlowLMは、Mimiが作るlatentを入力・教師信号として使い、その生成結果をMimi decoderに渡します。encoderを動かすと、この教師信号の座標系そのものが変わります。さらに、事前計算したlatentも古くなります。公式の学習コードではMimiを固定し、latent空間上でFlowLMを学習する設計です。

また、**現行のTTS学習lossにはMimi decoderを通した波形再構成lossがありません**。単にdecoderの`requires_grad`を有効にしても、decoderを適応させる学習にはなりません。MimiをFTする場合は、別途codec用の再構成学習経路を作る必要があります。

そのため、初回はMimiを動かさずに済むかを確認する方が、かなり進めやすいはずです。

## 4. 日本語では、Tokenizerとデータ処理の方が先に効きそうです

### テキストは「生日本語」を本線に、読み入力を比較用に

最終的に漢字かな混じりの文章をそのまま入力したいなら、まずはその表記で学習することを勧めます。

語彙数は、**日本語用SentencePieceの8kを初期案**にします。これは日本語で検証済みの最適値ではなく、漢字・かな・英数字を扱う余裕を持たせるための提案です。公式スクリプトは語彙数を変更でき、model config側の`n_bins`を一致させれば使えます。4k→8kで増えるEmbeddingパラメータは、幅1,024なら約410万です。

一方、読み誤りが多い場合には、**正しい読みを与えるかな／音素入力の別実験**を用意すると切り分けやすくなります。

- 読み入力なら良好：漢字の読みや表記-発音対応が主な課題。
- 読み入力でも悪い：音響モデル、データ対応、話者条件、終了判定などを疑う。

ただし、かな化やG2Pにも誤りが入り得るため、診断用データの読みは確認しておきます。また、かな入力専用モデルを作る場合は、その前処理を推論時にも必ず適用します。

なお、公式のTokenizer学習設定はbyte fallbackを有効にしています。したがって、**`<unk>`がゼロであることだけでは十分ではありません**。実際の日本語が何tokenに分かれているか、頻出の文字がbyte単位へ分解されていないかも見てください。

### 公式ローダーをそのまま使う場合の注意

現在のローダーは、同じ発話を単語境界で切り、

```text
前半の音声 → voice prompt
後半の音声 → 生成対象
後半の単語 → テキスト
```

として学習します。その際、後半の文字列を`" ".join(...)`で作っています。**日本語の形態素ごとにアラインメントを取ると、学習時だけ分かち書きになる可能性があります。** 学習・推論で表記を統一するか、文字オフセットから元の文字列を切り出すように変更する必要があります。

短い音声と正確な文単位の文字起こしがすでにあるなら、別の選択肢もあります。

> **生成対象は発話全体を使い、voice promptには同一話者の別発話を使うローダーにする。**

この構成なら、対象音声を途中で切らないため、必ずしも単語単位のforced alignmentは必要ありません。単語アラインメントはこのモデルの原理的な必須条件ではなく、主に公式ローダーの分割方式が要求しているものです。同一の対象音声をそのまま参照音声にも入れることは避けます。公式コードも、そのような重なりではテキストを読む代わりに音声をコピーする懸念を指摘しています。

また、`max_duration_sec`による音声の切り詰めに対して、文字起こしの末尾が自動的に同期して切られるとは限りません。**長い音声を上限時間で機械的に切るのではなく、対応の取れた短い発話に事前分割する**方が安全です。

### 推論側も日本語に合わせる

`text_chunking.py`の文末記号・分割記号は、主に英語向けです。日本語の`。！？、`を扱う分割を追加し、学習時と句読点の扱いをそろえることを勧めます。日本語前処理を外側で管理するなら、推論用configには次のような設定も考えられます。

```yaml
capitalize_first_letter: false
append_terminal_punctuation: false
```

これだけで日本語の文分割が完成するわけではありませんが、意図せず英語のピリオドを追加する処理などは止められます。

## 6. 評価と、その後の実験順序

最初の日本語先行実験で参考になるのは、**学習済み話者のサンプルは改善して聞こえる一方、未学習話者のvalidation lossは悪化した**という報告です。しかも最良validation時点のcheckpointが、直近3個だけ残す設定によって削除されています。声のクローニングを目指すなら、ここは避けたいところです。([Hugging Face](https://huggingface.co/ayousanz/pocket-tts-ja-phase1?utm_source=chatgpt.com))

私なら、評価を次の三つに分けます。

| 評価 | 見たいもの |
|---|---|
| 学習済み話者・未学習テキスト | 日本語の読み、音質、EOS |
| **未学習話者複数名**・未学習テキスト | 声のクローニングと汎化 |
| 読みの難しい専用テスト | 長音・促音、数字・助数詞、固有名詞、多音字、英数字混じり |

日本語ASRのCERに加えて、読み誤り、早期終了、無音継続、繰り返し、参照音声の内容をコピーしていないかを確認します。温度・CFG・EOS閾値は比較間でそろえ、**best checkpointを通常のローテーションとは別に保存**する運用を勧めます。

そのうえで、実験の優先順位は次のように考えます。

**まずLSD＋Mimi凍結で日本語を成立させる → データと読みの問題を改善する → 良い日本語教師から6層へ蒸留する。** 蒸留時は、公式方式に合わせてhead／EOSを固定し、conditioning dropoutをゼロにして、CFGを生徒へ焼き込みます。

Driftingを比較するのは、その基準モデルができてからがよいと思います。**最初に大きく変えるのは「言語とTokenizer」、Mimiと生成目的は維持する**という構成が、既存資産を活かしつつ、失敗原因も追いやすい出発点です。
