# PocketTTS 日本語FT 実験計画 v1

作成: 2026-10-09 / 元アイディア: [idea.md](idea.md) / 事前検証の詳細: [../reports/2026-10-09_precheck.md](../reports/2026-10-09_precheck.md)

ChatGPT案をそのまま骨格にする。

- 英語24層教師から始める
- 生成方式はLSD、Mimiは凍結
- 日本語SentencePieceを新規学習し、テキストEmbeddingは再初期化
- 最後に6層へ蒸留

このうえで、事前検証（§1）の結果と §9 の決定を受けて、次の点を具体化・修正した。

1. **データ**: Emilia と YODAS の重複を除くと 2.8kh ではなく **1.87kh**
2. **ローダー**: 同一話者の別発話を voice prompt に使う方式を主系に採用
3. **drop-in**: 公式推論コードの制約に合わせて、正規化と Tokenizer を設計
4. **評価**: JKYB-mini を学習中の主指標にする
5. **合成データ**: Irodori-TTS（MIT）で合成した読みの多い音声を、galleria2 で並行して作り、本線の学習データに混ぜる（§4.4）
6. **ログ**: progress.jsonl に加えて wandb に記録する（スカラーのみ。音声は送らない）

§9 の決定事項（2026-10-09 回答）を反映済み。

- データは Emilia + YODAS で、公開は NC になる。
- 24L 教師も公開する。
- 推論は現行 wheel への厳密な互換を条件とする。
- ReazonSpeech は使わない。Irodori の合成音声は積極的に使う。

## 1. 事前検証の結果（このセッションで実施）

### 1.1 Mimi（凍結）の日本語再構成 — M0

**設定**

- 対象: JVS 100話者の全14,982発話（30.2h、parallel100 / nonpara30 / whisper10 / falset10）。
- 処理: 公式の Mimi で encode → decode した。Mimi は全言語のリリースで同一の重みであることをハッシュで確認済み。
  - 一括 decode と公式のストリーミング decode の差は 0.1% 以下だった。
- 指標: JKYB と同じ正規化・ASR を使う。
  - **Kana-CER**: kana-whisper の出力を、JVS 音素ラベル由来の読みと比べる。
  - **Text CER**: whisper-large-v3-turbo の出力を、JVS の転記テキストと比べる。

**定量: 発話あたりの CER@1、全14,982発話。括弧内は差の 95% bootstrap CI**

| サブセット | n | Kana-CER 原音 → Mimi | 差 | Text CER 原音 → Mimi | 差 |
|---|---:|---:|---:|---:|---:|
| **朗読（parallel100 + nonpara30）** | 12,997 | 3.16 → 5.45% | **+2.29 [2.22, 2.35]** | 6.37 → 7.90% | +1.53 [1.44, 1.62] |
| 朗読・女性 / 男性 | 6,629 / 6,368 | 3.33 → 6.27 / 2.99 → 4.59% | +2.94 / +1.60 | 6.44 → 8.36 / 6.30 → 7.42% | +1.92 / +1.12 |
| falset10 | 985 | 3.41 → 9.11% | +5.71 | 6.86 → 10.13% | +3.27 |
| whisper10（ささやき） | 1,000 | 4.23 → 21.96% | +17.74 | 7.34 → 21.89% | +14.56 |

- Text CER は原音でも 6.4% ある。JVS の転記と Whisper の表記の揺れ（漢字かな、数字の書き方）によるもので、その分を差し引いて読む。
- 悪化が大きい話者の上位10名は全員女性だった（最大は jvs055 の +6.1pt）。高い F0 で劣化しやすい。

**増えた誤りの中身**（朗読音声、参照かな1,000字あたり）

- **子音の置換**（同じ母音で子音だけ違う）: +11.4。
- それ以外はわずか: 長母音 +0.8、促音 +0.1、撥音 +0.2、清濁 +0.6。
- 混同の上位はほぼ**調音位置**の取り違え: キ→チ、ガ→ダ、ニ⇄ミ、グ→ブ、ヒ→シ、カ→タ、ゴ→ボ、テ→ケ。
- ガ→ナ もあり、鼻濁音が関係していそう。

**読み精度への直接の影響**（最も判断に効く結果）

- JKYB の Irodori release 音声（13,536文、Accuracy 95.06%）を Mimi に通して再採点した。

| 指標 | Irodori 原音声 | Mimi 経由 |
|---|---:|---:|
| Accuracy | 95.06% | **93.28%（−1.78pt）** |
| Target Kana-CER@1 | 3.72% | 4.81% |
| Sentence Kana-CER@1 | 0.79% | 1.39% |
| Text CER@1 | 3.98% | 4.22% |
| 音読み / 訓読み / 付表 | 94.5 / 96.3 / 86.3% | 92.7 / 94.5 / 84.1% |

- 対応のある比較: Mimi で壊れた 274文、直った 33文（McNemar p≈2e-48）。
- 壊れた例もほとんどが子音の混同だった（互:タガ→タダ、仁:ニ→ミ、元:モト→ホト、係:カカリ→カタリ、元:ガン→バン）。

**情報が latent に残っているか**（M1 プローブ）

- 方法: CV モーラの子音を19クラスに分類する MLP を学習した。入力は onset 周辺 240ms。未学習話者20名で評価し、多数派ベースラインは 12.7%。
- 結果: **latent（3フレーム）から 94.1%** で識別できた（破裂音・鼻音だけなら 95.2%）。
- 比較: 80ms ブロック平均の mel では、原音 87.8%、再構成 88.8%。
- 10ms 解像度の mel では、原音 **93.0%**、再構成 **92.0%**（破裂音・鼻音は 93.6 → 92.7%）。
- まとめ: latent ≥ 原音 mel > 再構成 mel。
  - 子音の情報は latent に残っている。
  - **decoder の出力で約1pt 失われている**。ASR の Kana-CER では、これが +2.3pt（朗読）と大きく見える。

**定性**

- 試聴ページ: `exp/m0_mimi_recon/listening/index.html`
  - JVS の男女5名ずつ。F0 帯域が分散するように選んだ。
  - 各話者 parallel×2、nonpara、ささやき、ファルセットの計50対。
  - ローカル専用（JVS は再配布不可）。

**→ 判断**

1. **Mimi は凍結のまま進める**。
   - Mimi を通しても読みの上限は約93%（読みが Irodori v3 並みのTTSを前提とした目安）と見積もれる。
   - 目標の90%には余裕がある。
   - 長短母音・促音・撥音といったモーラ構造は保たれている。
2. ただし、**約1.8pt の天井低下と子音の不明瞭化は実在する**。
   - 子音の情報は latent に残っていて、主に decoder 側で失われている可能性が高い。
   - 対策は「**decoder だけの日本語FT**」（§5 M2）で、後から差し替えられる。
     - encoder と latent 空間を変えないので、FlowLM の再学習は不要。
     - Mimi の重みは配布する safetensors に同梱されるので、drop-in も保てる。
3. ささやき声とファルセットは大きく崩れる。
   - これらの話し方のクローンは対象外とし、評価は通常発声で行う。
4. ユーザーの主観評価（2026-10-09）
   - おおむね問題ない。高域がつぶれ 16kHz 相当に聞こえるが、英語オリジナルでも同じ。
   - whisper / falsetto が潰れるのは仕様として受け入れる。
   - **Mimi の改善（M2: decoder のみ）は、本学習が終わった公開前の段階で検討する。**

### 1.2 Emilia JA の構造と話者分布

全100シャードのメタデータを全数走査した（NAS上で約14分）。

| | Emilia JA | Emilia-YODAS JA |
|---|---|---|
| 発話数 / 時間 | 869,662 / 1,715.5h | 454,161 / 1,120.4h |
| ライセンス | **CC BY-NC 4.0** | **CC BY 4.0** |
| 形式 | WebDataset tar（json + mp3 24kHz）。32/64/160kbps が混在し、32kbps の約531hは約8kHzで帯域制限されている | 同（32/64kbps） |
| 発話長 | 3–30s（中央値5.4s） | 3–30s（中央値7.3s） |
| DNSMOS | すべて ≥3.0（中央値3.27） | 5%が <3.0（中央値3.21） |
| speaker ラベル | 59,663 | 34,050（20,861動画） |

- **重複が大きい**
  - Emilia の B00004–B00006（722h）は、YODAS とほぼバイト単位で同一（約95%）。
  - Emilia の B00000–B00003 の内部にも、(text, duration) の完全重複が21%ある。
  - 原因は、再アップロードされた JLPT 聴解やチャンネルの定型アウトロなど。
  - 重複を除くと **852k発話 / 1,870h**（Emilia由来1,440h + YODASのみ430h）。
  - **CC BY だけで構成すると、YODAS の重複除去後で 1,104h**。
- **speaker の意味**
  - 「1動画の中でダイアライズされた1話者」を表す。
  - Emilia の ID からは動画を復元できず、同一人物が複数の ID に分かれている。
  - そのため、話者分類器や評価用の held-out 話者の分割には、YODAS の動画対応表を併用する。
- **同一話者の別発話は十分ある**
  - 全発話の98%が「2発話以上を持つ話者」に属する（5発話以上なら93%）。
  - 重複除去後、5発話以上を持つ話者は 34k人 / 1,690h。
- **ラベルの純度**
  - 確認方法: ECAPA で、同一ラベル内の発話ペアと別ラベル間の発話ペアの類似度を比べた。
  - 平均類似度: 同一ラベル内 0.69–0.73、別ラベル間 0.15。EER は 1.6–3.7%。
  - 結論: ラベルはほぼ1人の声を指している。
  - 例外: JLPT 聴解やドラマなど、複数の声が1つの ID に入った話者がある。
  - 補足: WavLM-SV は、このデータでは識別力が弱い（EER 8–10%）。
- **テキスト**
  - 数字は算用数字で、13–17%の発話に含まれる。英字は6–15%。
  - `?!` は半角、`、。` は全角。
  - 英語だけの発話（0.2/1.5%）と、文字数が音声に対して極端に少ない／多い発話（約8.7k）は除去対象。

**→ 結論**: 「同一話者の別発話」を voice prompt に使うローダーは現実的。むしろ有利でもある。

- 同じ録音セッション・同じチャンネル特性のペアになる。
- forced alignment が不要になる。
- 推論時（別録音のプロンプト + 新しいテキスト）と同じ形になる。

### 1.3 Tokenizer（SentencePiece unigram）の粒度

Emilia 全文（正規化後130万文）で学習した。常用漢字とかなはすべて `required_chars` で必須にした。

| vocab | 文字/トークン | トークン/秒 p10 / p50（Emilia） | 公式の生成長上限を超える割合（Emilia / JVS朗読） | JKYB対象漢字: 語単位piece / 単漢字piece（熟語の内部） / 単漢字piece（それ以外） |
|---|---:|---:|---:|---:|
| 4k | 1.53 | 2.59 / 3.93 | 5.1% / **0.09%** | 3.5% / 57.0% / 37.1% |
| 8k | 1.83 | 2.09 / 3.24 | 10.2% / **0.60%** | 14.9% / 50.5% / 32.5% |
| 16k | 2.05 | 1.88 / 2.90 | 15.8% / **1.85%** | 27.0% / 43.5% / 27.6% |

- 日本語は必須文字だけで 2,313字ある。
  - **4k だと、語彙の過半を単文字が占める**。実質的に文字単位に近い入力になる。
- **公式推論の生成長上限**: `TTSModel._estimate_max_gen_len` は「トークン数/3 + 2秒」で打ち切る。
  - 語彙を粗くするほど、長い文の末尾が切れやすくなる。
  - 朗読（JVS、発話区間 + 0.3s で計測）では、8k まで実用上安全だった。
  - 公式チャンク上限は50トークン。これを中央値の話速で読むと 11.0 / 12.9 / 14.5 秒で、上限 18.7 秒に収まる。
  - 16k はゆっくり話す声で切れる危険がある。
  - Emilia の値が悪いのは、間や言い淀みを含む自発音声だから。
- Irodori の分析では、「熟語の中で単漢字トークンに分かれる」場合が読み誤りの最大要因だった。
  - ただし Irodori の誤りはテキストだけで事前学習した BERT エンコーダ由来であり、Pocket の LUT + 因果 Transformer にそのまま当てはまるかは不明。
- JKYB の文脈部分には、学習データで希少な非常用漢字（些・捧・鮭・絆 など217字）が byte fallback になって残る。
  - `character_coverage` を上げ、人名用漢字を必須文字に足して対処する。

**→ 方針**

- 本線は **8k**（ChatGPT案どおり）とし、Phase A のパイロットで 4k と比べる（§5 A5）。
- 16k は本線にしない。現行 wheel を厳守する（§9-3）ので、生成長の上限を変えられないため。
- 8k と 4k の差が小さければ、上限の余裕が大きい 4k を選ぶ。

### 1.4 学習スループット（RTX 5090、合成バッチ）

24L（学習対象 316M）、LSD、`flow_batch_multiplier` 4、bf16、層ごとの compile で計測した。

| micro-batch | target + prompt | ms/micro | 実効64の steps/s | ピーク VRAM |
|---:|---|---:|---:|---:|
| 16 | 8s + 6s | 70 | 3.6 | 10.4 GiB |
| 32 | 8s + 6s | 114 | 4.4 | 16.5 GiB |
| 64 | 8s + 6s | 219 | 4.6 | 28.8 GiB |
| 16 | 15s + 15s | 135 | 1.9 | 16.4 GiB |
| 16 | 30s + 30s | 268 | 0.9 | 28.7 GiB（32 だと OOM） |

- 設定: **micro-batch 16 × 勾配蓄積 4**（最悪長でも収まる）。余裕があれば 32 × 2 にし、target とプロンプトの合計長に上限を設ける。
- 見積もり: 本データの分布で実効 **2.5〜3.5 steps/s**。
- **計算量はボトルネックにならない**。15k step は約1.5h、100k step は約10h。
- 比較: 韓国語コミュニティモデルは 5090 ×4 で同じ実効バッチを回した。1枚だと wall-clock は約4倍になるが、それでも十分現実的。

### 1.5 公式推論 drop-in の制約（コード調査）

| 箇所 | 挙動 | 対応 |
|---|---|---|
| `tokenizer: sentencepiece` + `.model` | 公式でサポート済み。`n_bins` は語彙数と一致させる必要がある | config に指定する |
| `prepare_text_prompt` | 先頭文字を大文字化する。末尾が `.!?…` でなければ `.` を付け足す | `capitalize_first_letter: false`。学習テキストの句点は ASCII の `.` にそろえる |
| 文分割 `split_into_best_sentences` | `".!...?"` のトークンで文に分け、`",;:"` で再分割し、50トークンごとのチャンクを `" "` で連結する | 学習テキストの句読点を ASCII にし、文と文の間にスペースを入れる。推論時は `replace_characters` で `。、？！` を写像する |
| `_estimate_max_gen_len` | 生成長の上限 = トークン数/3 + 2秒 | Tokenizer の粒度で担保する（§1.3）。**現行 wheel を厳守**する（関連する upstream PR #194 は進捗がなく、前提にしない） |
| CFG | 公式推論には CFG がない（cfg=1 固定） | 配布するモデル（6L・24L とも）は CFG を焼き込む（§5 D0/D1） |

| 正規化 | Tokenizer は identity 正規化で、NFKC はかからない | 全角英数字の写像も `replace_characters` に列挙する（`pocket_tts_ja.text.inference_replace_characters()`） |
| 長いプロンプト | upstream #344 の報告: 5秒のプロンプトだけで学習した6L生徒は、12秒を超えるプロンプトで早期EOSになった。公式APIはプロンプトを全長のまま渡す | **学習時にも 3–30秒の全長プロンプトを使う**（別発話ローダーなら自然にそうなる） |

## 3. 全体方針

```
            本機（学習）                                  galleria2（生成・評価）
Phase A  パイプライン → スモーク → パイロット            S0–S2  Irodori 合成データの準備・生成・QC
         （実データのみ, 24L LSD, 15k step, 4k/8k 比較）        （A の間に約20〜30万文を作る）
Phase B  本学習（24L 教師, 実データ + 合成 約15%,       ←  S の latents を合流
         〜100k step）＋ 限定アブレーション                  チェックポイントの JKYB / JVS 評価を非同期で回す
Phase C  読み精度の改善（B が 90% に届かない場合）       ←  C0 の誤り語を狙って追加合成
         診断 → 追加合成 / かな置換自己蒸留 / 補助損失 / Mimi decoder FT
Phase D  24L の CFG 焼き込み（公開用）＋ 6L へ深さ蒸留 → wheel 形式でパッケージ → 再評価
Phase E  （任意）Drifting 比較、数字・英字・長文・短文の頑健化
```

試聴は待たずに学習を進める。試聴ページはマイルストーンごとに用意し、後から確認してもらう。

決定事項（ChatGPT案との差分を含む）。

1. **初期値と学習方式**
   - `english_2026-04_24l` から始め、テキストEmbeddingは再初期化する。sampler head・EOS head・各射影は引き継いで学習する。
   - LSD + Mimi凍結（§1.1で裏付け）。
   - lr は 2e-4 で一定、warmup 1k。実効バッチ64を勾配蓄積で作る（公式の品質遷移の条件）。
2. **ローダー**: **同一話者の別発話を voice prompt にする**ローダーを自作する（§4.3）。
   - target は発話全体、text は全文。
   - Mimi latents は事前計算しておけば足りる。学習中は音声を読まないので、NASがボトルネックにならない。
3. **テキスト**: 漢字かな交じりの生テキストを使う。正規化は `pocket_tts_ja.text.normalize`（§4.2）。
4. **Tokenizer**: SentencePiece unigram、本線 8k（4k と比較）。常用漢字・人名用漢字・かなは必須文字にする。
5. **評価**（§6）
   - 学習中の主指標: **JKYB-mini（1,500文、層化抽出）**。
   - マイルストーン: JKYB 全13,536文。
   - 声クローン: JVS 100話者ゼロショット。
   - チェックポイントはローテーションで消さない。`num_ckpt_keep` を大きくし、JKYB-mini のベストを別に保存する。
6. **合成データ**: Irodori-TTS-v4.1-Small-Yomi（v3、JKYB 95.7%、MIT）で合成した読みの多い文を、実データに約15%混ぜる（§4.4）。
   - 権利的に最もクリーンで、Emilia に少ない語の読みを直接補える。
   - 生成は galleria2 で、学習と並行して行う。
   - ReazonSpeech は使わない。16kHz で音質が厳しいため。
7. **ログ**: wandb にスカラーだけを送る。`scripts/train_ja.py` で公式の `ProgressLog.log` をフックし、評価スクリプトも同じ run に `step` 付きで書き込む。

## 4. データパイプライン

### 4.1 前処理とフィルタ（`scripts/prepare_emilia_ja.py`、Phase A0）

出発点は survey で作ったメタデータ表 `exp/emilia_survey/emilia_ja_meta.parquet`（全発話のtarオフセットつき）。ここに次の順でフィルタをかける。

| 段 | 規則 | 残量（目安） |
|---|---|---|
| 1 | 重複除去（text + 10ms精度のduration + mp3サイズ。最初の1件を残す） | 852k / 1,870h |
| 2 | かな・漢字を含まない発話（英語のみ）を除去 | −約20h |
| 3 | 文字/秒が 1.5〜15 の範囲外（文字起こしの欠落やASRの繰り返し）を除去 | −約1% |
| 4 | DNSMOS < 3.0 を除去（YODAS 側のみ該当） | −約50h |
| 5 | 1発話しかない話者を除去（別発話プロンプトが作れないため） | −約2% |
| 6 | **話者一貫性**: ECAPA埋め込みと話者重心のcosが0.35未満の発話を除去（複数の声が混じったラベル対策） | −数% |
| — | 32kbps（8kHz帯域）は除去しないがタグを付ける。プロンプトに使ってよいかは B で検証 | — |

- 最終的に **約1.7kh / 約80万発話**を見込む。
- 数字と英字は残す。読みはデータから学習させ、頑健化は Phase E で行う。
- **latents の事前計算**（`scripts/precompute_ja.py`）
  - 手順: NAS 上の tar をシーケンシャルに読み → mp3 をデコード → 24kHz にする → Mimi で encode する。ECAPA 埋め込みも同じパスで計算する。
  - 出力: `data/emilia_ja/latents/*.safetensors` と、`latents_file` 列つきのマニフェスト。
  - 容量は約12GB（1.7kh × 7.3MB/h）。
  - 所要時間の見積もり（未計測）: NAS 読み出しが約15分（110GB / 130MB/s）、Mimi encode が数時間。M0 の round trip は約600倍速だった。
- **分割**
  - valid: 学習に出ない話者で約0.5%。YODAS は動画単位で切り、Emilia は動画対応表で同一動画の ID をまとめて除外する。
  - JKYB の文が学習テキストに含まれていないか、完全一致で確認する。

### 4.2 テキスト正規化（学習・推論共通、実装済み: `src/pocket_tts_ja/text.py`）

1. NFKC（全角英数字・`？！` を半角にする）。
2. `。．→.`、`、，→,`。
3. 括弧・引用符（`「」『』（）【】“”` など）は削除する。
4. `…` 系を統一し、繰り返しの句読点は1つに縮める。
5. **文末記号の後に半角スペースを入れる**。公式チャンカーの `" ".join` と分布をそろえるため。
6. 数字・英字はそのまま残す。

推論 config: `replace_characters` に同じ写像（124文字）を入れ、`capitalize_first_letter: false`、`append_terminal_punctuation: true`、`remove_semicolons: true` とする。

### 4.3 ローダー（`src/pocket_tts_ja/loader.py`、upstream は改変しない）

- 実装方針
  - 公式の `DataLoader` を継承する。`train.py` が使う `SubprocessDataLoader` / `DataLoader` を差し替える薄いラッパー `scripts/train_ja.py` を用意する。
  - 子プロセスは spawn で起動されるので、子プロセスの入口関数ごと自前で用意する。
- サンプリング
  - target: 発話 i の latents 全体（≤30s）。text: 発話 i の全文。
  - **voice prompt**: 同じ話者の別発話 j（j ≠ i、text が異なるもの）の latents。
- プロンプト長の分布
  - 50%: 先頭を一様に 3–10s で切り出す。
  - 35%: 発話全体（3–30s）。
  - 15%: 同じ話者の発話2つを連結して 10–30s にする。
  - これで全長プロンプトに頑健にする（#344 の教訓）。
- 公式由来の拡張
  - `prompt_trim_max_sec: 0.5`、`final_punct_dropout: 0.3`（ASCII の `.` を対象）。
  - CFG dropout: text 0.2 / voice 0.2。
- stitch は不要
  - 公式の latents モードは、カット点の直後を音声から再エンコードする（stitch）。
  - 本方式では target・プロンプトとも発話の先頭から encode した latents をそのまま使う。Mimi encoder は因果的なので、先頭からの切り出しはコールドスタートの encode と一致する。
- 比較用: 公式の同一発話分割（forced alignment）
  - 将来、比較アブレーションとして用意する（B5）。
  - aligner は Qwen3-ForcedAligner-0.6B（日本語対応。韓国語コミュニティモデルが使用）を想定する。
- 合成データの混合
  - マニフェストの `source` 列（`emilia` / `yodas` / `irodori`）を見て、バッチ内の比率を指定できるようにする（既定は合成 15%）。

### 4.4 合成データ（Irodori-TTS、galleria2 で生成）— S0〜S3

**目的**

- Emilia（自然発話・YouTube）には、熟語・付表語・訓読みの稀な読みが少ない。
- そこで、読みの正しさを検証済みの合成音声で直接補う。
- 権利面: 教師は MIT で、テキストは KANJIDIC2・JMdict（CC BY-SA）・Wikipedia（CC BY-SA）・青空文庫（PD）に由来する。

**ステップ**

| ID | 内容 |
|---|---|
| S0 | **環境**: galleria2 の Irodori-TTS 環境に、本機の `Irodori-TTS-v4.1-Small-Yomi`（v3）をコピーする。Irodori の標準設定（RF 40 step、CFG text 3.0 / speaker 5.0、DiT は bf16、テキストエンコーダと codec は fp32。bf16 のエンコーダは約0.5pt 悪化するため）でスループットを確認する。目安は 11.2 文/s |
| S1 | **テキスト**（目標 20〜30万文）: 下表の (i)〜(iii) を混ぜる |
| S2 | **声**: Emilia / YODAS の高品質クリップ（DNSMOS ≥3.3、64/160kbps、話者一貫性フィルタ済み）から約3,000話者を選び、参照音声にする。1つの参照で約80文を合成する |
| S3 | **QC と変換**: kana-whisper で読みを検証し、Mimi latents に変換して本機へ転送する |

**S1 のテキスト内訳**

| 種類 | 内容 | 件数 |
|---|---|---:|
| (i) 読みの多い文 | Irodori 実験の**本番段階の行**（KANJIDIC2 ベース。`rows_prod / aozora / aozora2 / var / contrast`）。JKYB のキー由来の初期の行（`pilot / m3 / kun`）は使わない | 約22万行 |
| (ii) 稀語を含む文 | Wikipedia（ローカルに約310万文）から、本データの学習テキストで出現が少ない漢字語を含む文を選ぶ | 約5万文 |
| (iii) 一般文 | 話し言葉寄りの一般文。韻律と語彙の偏りを和らげるため | 約3万文 |

- 除外: JKYB の文（完全一致と n-gram の近似重複）、青空ルビ評価セットの作品。

**S2 の話者ラベル**

- 合成側の話者ラベルは `syn:<参照話者>` とする。
- ローダーのプロンプトは、**参照に使った実音声**（50%）か、同じ参照で合成した別の文（50%）にする。
- 実音声のプロンプトから合成音声の target を作る形を必ず含め、声クローンの汎化を保つ。

**S3 の採用条件と変換**

- 採用条件
  - kana-whisper の読みが行の `yomi` と比べて Sentence Kana-CER ≤ 5%。
  - 対象語の読みが一致する。
  - 不合格の文は seed を変えて1回だけ再生成する。
  - こうして、Irodori 自身の誤読（約4%）を学習させないようにする。
- 変換: 48kHz → 24kHz → Mimi latents。latents は galleria2 で計算して転送する（約3〜5GB）。

**規模と所要時間**

| 規模 | 合成 | ASR の QC（28文/s） | encode |
|---|---:|---:|---:|
| 30万文（約300〜450h） | 約7.5h | 約3h | 約1h |

- 合計で galleria2 の約半日。本機で A0〜A5 を回している間に終わる。

**注意点**

- Irodori 特有の韻律や声のくせが乗る。DACVAE → Mimi の二重コーデックになる点もある。
- 対策
  - 混合比は 30% を上限にする。
  - 評価は常に実音声（JVS）のプロンプトで行う。
  - 合成の比率は B3 で決める。

**Phase C での追加生成**

- C0 で特定した誤り語について、例文を新しく作る（LLM か Wikipedia 検索）。
- それを追加で合成する。これがハードマイニングになる。

### 4.5 YODAS3 ja（CC-BY 3.0、約17kh）— Y0〜Y3（2026-10-09 追加）

ユーザーの提案で追加した。upstream #344 が仏・伊・蘭・独の 24L の仕上げに使ったのと同じ系列のデータで、ライセンスは **CC-BY 3.0**。

**メタデータの全数集計**（108シャード。置き場は `/mnt/artifacts/yodas3`）

| 項目 | 値 |
|---|---|
| 動画数 / 時間 | 79,962 / **17,404h**。うちキャプションが覆う区間は 14,019h |
| キャプション | YouTube の自動字幕 16,931h（単語ごとの開始時刻あり）、アップロード者の字幕 465h |
| 音質 | Opus 約125kbps。max_freq の中央値は約20kHz で**全帯域** |
| 形式 | 動画単位の webm（約8GB の tar ×108、合計約860GB） |
| ないもの | 話者ラベル、発話への分割、品質スコア |

**判断**

- 量は Emilia（重複除去後 1.87kh）の約9倍で、音質も Emilia の mp3（8〜11kHz）より良い。
- これを使えば、**CC-BY 系だけのモデル**を作れる見込みが出てきた。
  - 構成は YODAS3 + Emilia-YODAS（CC BY 4.0）+ Irodori 合成（MIT）。
- 一方で、Emilia-Pipe に相当する前処理は自前で作る必要がある。
- そこで次の手順で進める。
  1. 1〜2シャードでパイロットを回し、ラベルの品質と残る量を測る。
  2. 結果を見て、全量を処理するかを決める。

**手順**

| ID | 内容 |
|---|---|
| Y0 | ダウンロード（galleria2 から `/mnt/artifacts/yodas3`、約74MB/s で約3.2h）とメタデータの集計（上表） |
| Y1 | `scripts/yodas3/process_shard.py` で、シャードごとに次を行う（下記） |
| Y2 | `scripts/yodas3/finalize_yodas3.py` でフィルタ・ラベル付け・話者クラスタリングを行う（下記） |
| Y3 | パイロット評価: ランダムな100件を試聴し、合意率・残存時間・話者数を測る。全量処理の GPU 時間を見積もる |

**Y1 の処理内容**

1. webm を PyAV でデコードする。
2. silero VAD をかけ、0.5s 以上の無音で切って 3〜20s の発話にまとめる。
3. キャプションの単語を時刻で発話に割り当てる。
4. DNSMOS P.835 を計算する。値は Emilia の格納値とほぼ一致することを確認した。
5. whisper-large-v3-turbo で書き起こす。
6. ECAPA の話者埋め込みと Mimi latents を計算する。

**Y2 のフィルタとラベル**

| 対象 | 内容 |
|---|---|
| 字幕との一致（caption agreement） | YouTube 字幕と Whisper の書き起こしを、pyopenjtalk の読みに直して CER を取る。≤0.10 を採用 |
| 音質 | DNSMOS OVRL ≥3.0 |
| 話速 | 文字/秒が 1.5〜15 |
| 学習ラベル | Whisper の書き起こし。句読点つきで、Emilia と同じ表記スタイルになる |
| 話者 | 動画内で ECAPA 埋め込みを平均連結法で階層クラスタリングし、2発話以上のクラスタを話者とする |

**パイロット結果**（シャード 0002、691 動画）

| 段階 | 値 |
|---|---|
| Y1 の出力 | 28,119 発話 / 77.4h。galleria2 の GPU を合成と共有して 34.9 分 |
| 字幕との一致 CER | 中央値 0.10、p25 0.04、p75 0.22。フィラーを除き、境界の語には寛容な指標（`supported_cer`）で測った |
| 主な不一致の原因 | フィラー、境界の語、英単語。数字の表記違いは読みに直すと吸収される |
| ラベル | Whisper の方が概ね正確（電子シャッター／電子アタ、暴れん坊将軍／アバレン暴軍）。Whisper 側の誤りは、主に読みが同じ漢字の取り違え（急進派→旧新派） |
| 合成音声チャンネル | **290 クラスタ / 5,861 発話**を「量産声」として除外した。中身はすべて Wikipedia の合成音声読み上げだった |
| 残存（一致の閾値ごと） | ≤0.10: 7.8h（109話者）、≤0.15: 9.8h、≤0.20: 11.0h。歩留まりは約10〜14% |

→ 全 108 シャードを処理すると、**約850〜1,200h** の CC-BY データが見込める。

**処理の順序**

- B1 の律速は S3（合成）なので、galleria2 では S3 を優先する。
- YODAS3 の全量処理は S3 の後に回す。全量で GPU 2〜3日程度。
- その前に、Whisper を通す対象を減らす。
  - DNSMOS < 2.9 の発話は Whisper にかけない。
  - 既知の合成音声（量産声）の埋め込みに近い発話もかけない。
  - 合わせて約3〜4割の削減を見込む。

**GPU コスト**

- 主な負荷は Whisper。見積もりは約300〜400倍速で、全量を処理すると1枚で約1.5日、2枚で約1日。
- パイロットの結果を見て、処理するシャード数を決める。

**ライセンス上の位置づけ（案）**

- B1 の本線データを「YODAS3 + Emilia-YODAS + 合成」とすれば、CC-BY で公開できる。
- Emilia（NC）は、加えて効果があればアブレーションとして扱う。
- 両方を作る場合は、配布物を2系統に分ける。

### Phase C — 読み精度の改善（B1 が頭打ちの時点で JKYB < 90% の場合）

| ID | 内容 | 根拠・注意 |
|---|---|---|
| C0 | **診断** | 打ち手を選ぶための前提 |
| C1 | **かな置換・自己蒸留データ** | Irodori で効いた方法を Pocket 向けに単純化したもの。latents が Mimi のままなので、コーデックの不一致がない |
| C2 | **ハードマイニング合成**（Irodori）: C0 の誤り語について新しい例文を作り、追加で合成する | 本線 S の延長。語あたりの例文の多様性が効く（Irodori で、語あたり6例文にすると未学習文の正答率が +14pt） |
| C3 | **補助的な読み損失**（学習時だけの head で、推論では捨てる。drop-in を維持できる） | |
| C4 | Tokenizer の変更（C0 の結果、誤りが「熟語内の単漢字」に集中していた場合） | |
| M2 | **Mimi decoder の日本語FT**（encoder と latent は固定）。**本学習後、公開前に検討する**（ユーザー判断）。C0 で子音の混同が誤りの主因だった場合は前倒しも考える | §1.1 の M0/M1 より、天井が約1.8pt 下がっており、情報は latent に残っている |

**C0 診断**

1. 誤りを分類する。Irodori の `analyze_jkyb_errors.py` を自前の SentencePiece 向けに移植する。
2. **かなオラクル**: 対象語をカタカナに置き換えて生成する。
   - 正解率が大きく上がる → テキスト側の問題。
   - 上がらない → 音響側の問題。
3. 対象語が学習テキストに出てくる頻度と正解率の関係を見て、データの不足量を定量化する。

**C1 かな置換・自己蒸留データ**

1. 読みつきテキストを用意する。Irodori で作った約34万行（LLM 例文・Wikipedia・青空文庫ルビ）を使う。**JKYB の文は除外**する。
2. 自モデルに「難語をカタカナにした文」を入力して latents を生成する。
3. 漢字の原文とその latents を対にして、学習に10%程度混ぜる。

**C2 ハードマイニング合成**

- 手順は §4.4 と同じ（Irodori-TTS v3 + 実話者の参照 + kana-whisper の QC）。
- 対象語は C0 の誤り語に絞り、1語あたり6文以上の多様な例文を用意する。

**M2 Mimi decoder の日本語FT**（galleria2 で並行して実施できる）

- encoder と downsample は凍結し、decoder 側（upsample、decoder transformer、SEANet decoder）だけを学習する。
  - latent 空間は変わらないので、学習済みの FlowLM はそのまま使える。
  - 配布する safetensors の `mimi.*` を差し替えるだけで、drop-in を保てる。
- 損失: multi-scale mel、MS-STFT 識別器（敵対的損失と特徴マッチング）、元の decoder 出力との距離（忘却を抑える）。
- データ: Emilia の 160kbps・高 DNSMOS の発話と、Irodori の合成音声（帯域が広くクリーン）。JVS は評価専用にする。
- 評価: M0 の手順（JVS の Kana-CER、JKYB の Irodori 音声を通した Accuracy）。目標は −1.78pt の差を半分以下にすること。
- 注意: mp3 由来の帯域制限（約11kHz）を decoder が覚えないよう、合成音声と高ビットレートの音声に限る。

**C3 補助的な読み損失**

- text 位置の hidden を4倍にアップサンプルし、CTC でカナ列を予測させる。
- 正解の読みは Sudachi / pyopenjtalk で付与した Emilia 文字起こしの読み（ノイズはあるが、解析器間の一致率は97%）。

**汎化の確認（JKYB への過適合を避ける）**

- C で何かを足したら、JKYB 以外の評価も必ず見る。
  - 青空文庫のルビ付き評価文3,000（Irodori で作成済み、JKYB 形式）。
  - JSUT BASIC5000 のかなCER。
- 語の選定に JKYB のキーは使わない（Irodori のリーク対策を踏襲）。

## 6. 評価プロトコル

| 評価 | 内容 | 頻度 |
|---|---|---|
| valid loss | held-out 話者の flow loss / EOS loss | 1k step ごと（学習ループ内） |
| **JKYB-mini** | `data/eval/jkyb_mini.jsonl`（1,500文。読みのペアごとに1文、カテゴリ比率は全体と同じ）。`jkyb-eval tts --dataset` で採点 | 2.5k step ごと |
| **JKYB full** | 13,536文。カテゴリ別、McNemar で前回と比較 | マイルストーン（20k / 50k / 100k、蒸留後） |
| JVS ゼロショット | 100話者 × parallel100 から10文。プロンプトは同じ話者の nonpara30 の発話。Text CER、Kana-CER（ラベル由来の読み）、話者類似度（ECAPA。WavLM-SV は参考値）、UTMOSv2、no-EOS・無音の件数。M0 の再構成値を上限の目安にする | 5k step ごと（100件版）、マイルストーンで1,000件 |
| 試聴 | JVS 男女5名ずつ × 5文 + JKYB の難文。HTML で並べる（M0 と同じ形式、ローカルのみ） | マイルストーン |
| 汎化 | 青空ルビ評価、JSUT かなCER | Phase C 以降 |
| drop-in | 公式 CLI で生成した音声に対する JKYB-mini | Phase D |

生成条件は固定する。

- temp 0.3、LSD 1 step、`eos_threshold -4`（公式の推論既定）。
- CFG は教師 2.0、蒸留後 1.0。
- seed は 0 で固定。
- プロンプトは JVS の4話者（男女2名ずつ）を文の key のハッシュで割り当てる。比較用に、Irodori と同じ `jvs001/VOICEACTRESS100_001` 固定の条件も1つ持つ。

GPU バッチ生成（`TrainableTTS.generate`）を使えば、JKYB-mini は生成とASRを合わせて約5分、JKYB 全文は約30分で回る見込み。

学習と同じ GPU で回すと VRAM が足りない。そこで、評価は **galleria2 で非同期に回す**。

- 手順
  1. 新しいチェックポイントの EMA 重み（`model.safetensors`、約1.3GB）を rsync で galleria2 に送る。
  2. 評価キューが JKYB-mini と JVS を回す。
- 合成ジョブとは時間を分けて使う。
- galleria2 が使えないときは、学習を一時停止して本機で評価する。

**ログ（wandb）**

- project は `pocket-tts-ja`。run 名は実験 ID（例: `A5-8k`）。
- 学習
  - `scripts/train_ja.py` で公式の `ProgressLog.log` を包み、`train` / `valid` イベントのスカラーを `wandb.log(step=...)` に流す。
  - 送るスカラー: loss、flow / EOS の loss、lr、grad norm、it/s。
- 評価
  - 評価スクリプトは、学習の run id に `resume="allow"` で接続する。
  - 送る指標: `eval/jkyb_mini/acc`、カテゴリ別、`eval/jvs/kana_cer`、`sim`、`no_eos` など。
  - 学習の step に揃えて送る。
- **送らないもの**: 音声、スペクトログラム画像、チェックポイント、大きな Table。
  - 試聴音声と生成物は `exp/` と `runs/` に置き、ローカルに残すだけにする。
- 設定値（解決済みの config）は `wandb.config` に入れる。git の commit も記録する。

## 7. リスクと対策

| リスク | 兆候 | 対策 |
|---|---|---|
| データの読みカバレッジ不足で JKYB が頭打ちになる | 熟語・付表語・訓読みで誤りが多い | 最初から Irodori の合成データを混ぜる（§4.4）。それでも足りなければ Phase C（C0 で切り分けてから C1〜C3、M2） |
| 合成データの癖を学習する | 韻律が単調になる、Irodori の声質に寄る、実音声プロンプトでの類似度が下がる | 混合比は最大30%（B3 で決める）。実音声のプロンプトと組み合わせる。JVS（実音声）で評価する |
| Mimi による天井の低下（−1.8pt、子音の混同） | 生成音声の誤りが子音の混同に偏る | M2（decoder FT）。latent は変えないので、後から差し替えられる |
| Emilia の文字起こし誤り（Whisper の幻覚・欠落） | Text CER が下がらない、余計な発話を挿入する | フィルタ段3。必要なら別系統のASRとの一致度でフィルタする（公式 #344 も YODAS を caption agreement でフィルタしている） |
| 複数の声が混じった話者ラベル | 声クローンの類似度が低い | ECAPA で話者一貫性フィルタ（段6） |
| 低帯域（32kbps）を学習する | プロンプトなし・低品質プロンプトでこもった音になる | タグを付け、プロンプトから除外するかを B4 で検証 |
| 長いプロンプトで早期EOS（#344） | 12s 超のプロンプトで発話が途中で切れる | 全長プロンプトと連結プロンプトで学習（§4.3）。E2 で掃引 |
| drop-in の生成長上限（現行 wheel を厳守） | 長文の末尾が切れる | 8k 以下にする。4k と差がなければ 4k にする。E2 でゆっくり話すプロンプト × 長いチャンクを検証する |
| VRAM（32GB） | 30s 発話 + 30s プロンプトで OOM | 長さバケット。発話長とプロンプト長の合計に上限を設ける。§1.4 で上限を確認 |
| 過学習（先行の日本語 phase1 では 7.5k step 以降に valid loss が悪化） | 未学習話者の loss が上がる | データ量は約20倍。チェックポイントは全部残し、JKYB-mini で選ぶ |

| JKYB へのリーク | — | 学習テキストとの完全一致チェック。Phase C のデータから JKYB の文を除外。汎化指標も併記する |

## 8. 計算予算とスケジュール

GPU 時間の見積もりは §1.4 の実測から出した。実装に要する時間は含まない。

| 段階 | 主な計算 | GPU 時間 |
|---|---|---|
| A0 | NAS からシーケンシャルに読み（約15分）→ mp3 デコード → Mimi encode + ECAPA（1.7kh） | 3〜5h（1回だけ） |
| S0〜S3（galleria2） | Irodori で30万文を合成し、kana-whisper で QC、Mimi encode | 約12h（A と並行） |
| A3 | スモーク 2k step | 0.3h |
| A5 | パイロット 15k step × 2（4k / 8k）+ JKYB-mini × 6点 × 2 | 4〜5h |
| B1 | 100k step + JKYB full × 3、JKYB-mini × 40 | 12〜15h |
| B2〜B4 | 15k step × 最大3（B3 は合成比率 0 / 15 / 30%） | 〜6h |
| C | データ生成（10万文、24L バッチ生成）+ 追加学習 20〜30k step | 5〜8h／1サイクル |
| D0 | 24L CFG 焼き込み（同じ深さの distill、50k step 程度） | 約6h |
| D1 | 6L 蒸留 50k〜200k step（英語の公式値は H100 で 10.5 steps/s、5090 ではその半分程度と仮定） | 3〜11h |
| M2（任意、galleria2） | Mimi decoder FT | 1〜2日（実装を含む） |
| 評価 | JKYB full 1回 ≒ 30分（生成とASR） | — |

本線（A → B1 → D1）の GPU 時間は約 1.5〜2日。

アブレーションと Phase C を含めても、GPU 時間は1〜2週間に収まる見込み。

進め方（初回）

1. 本機で A0〜A2 を実装し、A3 のスモークまで回す。並行して galleria2 で S0〜S3 を進める。
2. A5 のパイロット（4k / 8k、実データのみ）を走らせ、JKYB-mini の推移を wandb とレポートで報告する。
3. 結果を見て Tokenizer を確定し、合成データを合流させて B1 を始める。試聴は待たずに進める。
